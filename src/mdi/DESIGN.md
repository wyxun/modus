# MDI 框架设计

本文是 `modus/src/mdi` 的稳定设计说明。它描述接口边界和实现规则，不记录开发阶段
的尝试、阶段任务或临时方案。应用使用说明和具体 API 示例见同目录的 `README.md`。

## 设计目标

MDI（MODUS Device Interface）把 MCU 能直接完成的硬件工作抽象成编译期确定的资源，
让应用和芯片无关驱动调用统一的硬件语义，同时保留底层调用的实时性能。

目标包括：

- 应用不依赖 STM32 HAL、厂商对象或芯片外设编号；
- GPIO、采样帧、PWM、总线事务等能力有明确的单位、状态、所有权和生效时刻；
- 同一组操作可以一次完成，例如一次读取三相采样帧或一次提交三相 PWM；
- 热路径不经过运行时对象查找、`void *` 上下文、函数指针或通用命令分发；
- 新芯片通过后端和实例绑定接入，不修改公共契约和应用调用。

“零开销”只表示相对于同一寄存器工作、检查和时序语义的手写实现不增加抽象层开销。
I2C/SPI 协议循环、DMA 同步、整数换算、故障判断和必要的范围检查仍然需要实际指令。

## 源码分层

```text
应用 / 通用驱动
        │  MDI_* 宏、类型化帧、mdi_status_t
        ▼
modus/src/mdi/core/       公共契约和编译期绑定模板
modus/src/mdi/feature/    I2C、SPI、软件协议和设备组合能力
        │  资源 token 在编译期绑定
        ▼
peripheral/<chip>/mdi/    芯片寄存器后端和 instance.h
        ├── state.c        DMA/Stream 等共享存储
        └── service.c      mdi_Init/mdi_Service/mdi_Clock 板级维护
        ▼
寄存器、IRQ、DMA、时钟和板级安全资源
```

- `core/` 不包含厂商头文件、板卡名称或外设编号。
- `feature/` 只组合已有能力，不选择芯片，不保存运行时设备对象。
- `peripheral/<chip>/mdi/` 负责寄存器表达式、资源映射、初始化入口和安全生命周期。
- `peripheral/<chip>/mdi/state.c` 只提供静态绑定所引用的板级共享存储；`service.c` 实现
  `mdi_Init()` / `mdi_Service()` / `mdi_Clock()`，不创建聚合 `HW` 对象。
- `legacy/` 只用于迁移旧对象/函数指针接口，不能进入新的实时路径。

芯片后端可以使用 CMSIS 或厂商库完成时钟、复位、复杂 DMA 和非实时初始化；公共 MDI
不依赖这些库，实时 provider 应直接落到寄存器或等价的 `static inline` 操作。

## 核心不变性与扩展边界

`core/` 的接口数量和语义必须保持小而稳定。新增外设或应用模式时，先判断它是否改变
了以下不变量：

- 资源 token 在编译期绑定，不变成运行时索引、对象指针或函数表；
- 热路径直接访问 provider，不能重新引入 `void *`、函数指针或通用分发；
- 一次操作的单位、完成时刻、所有权和错误状态必须可以在契约中说明；
- core 只描述跨芯片都成立的硬件原语，不携带 FOC、传感器、存储器或板卡策略；
- 不具备能力的资源不提供成功 stub，能力差异必须在绑定或状态码中显式体现。

如果需求只是把已有原语组合成新的采集流程、协议或滤波方式，应新增或扩展
`feature/`，而不是把参数和分支塞进 `core/`。例如 ADC/DMA 完成标志、多次采样均值、
中值滤波、IIR 滤波和 tick 调度都属于 feature；core 只需要保留 ADC 单值读取、稳定帧
读取和基本状态语义。feature 可以接受编译期参数，也可以组合多个 core 资源，但不能
改变 core 接口的含义。

编译期参数应放在芯片 `instance.h` 或 feature 绑定宏中。运行时参数只有在硬件确实
需要动态改变时才开放，并且必须说明额外的状态、同步和执行成本。采样次数、DMA 缓冲
布局和通道顺序通常会影响内存与代码生成，优先作为编译期参数；不同采样策略通过不同
feature 或多个采集组组合，而不是让 core 变成一个运行时模式机。

## 静态绑定规则

资源 token 是预处理 token，不是运行时设备索引。例如：

```c
MDI_PWM_REG_BIND(bridge, BRIDGE_CHANNELS)
MDI_PWM_SetDuty(bridge, &tDuty);
```

绑定宏会生成具体类型和函数名。宏本身不是零开销证明，后端必须同时满足：

1. 展开结果不创建设备描述符或运行时查找；
2. provider 不经过 `void *`、函数指针、虚表或通用分发器；
3. 多通道工作由一次类型化帧完成，不让应用重复进入同一层；
4. `*_Fast` 只省略已经由调用者承担的检查，不能绕过故障和所有权规则；
5. 在 `-O2/-Os` 下检查汇编，热路径不能出现不必要的 `bl` 或间接调用。

如果一个宏最终调用普通函数、函数指针或 HAL 分发器，它只是语法包装，不属于 MDI 的
静态热路径。

## 公共能力契约

### IO

IO 是右对齐的逻辑位向量，支持单 pin、跨端口向量和掩码写。绑定提供宽度和输入、输出、
开漏能力标记。芯片负责 GPIO 模式、上拉、复用和资源所有权；`MDI_IO_Read` 读取管脚
状态，`MDI_IO_Write` 只修改绑定的物理位。

### 采样

`MDI_Sample_Frame(R)` 是资源定义的强类型帧。读取接口只消费已经完成的数据，不启动或
等待转换。稳定帧通过序列号或硬件完成标志保护生产者所有权；完成标志的清除顺序由芯片
后端定义。

### PWM

PWM 将通道帧、周期、占空比、提交和生命周期分开：

- `MDI_PWM_SetDuty` 接收有单位的 Q16 duty 帧并执行检查；
- `MDI_PWM_StageFast` 接收调用者已经验证的 timer tick 帧；
- `MDI_PWM_Commit` 请求硬件更新事件；
- `MDI_PWM_Enable`、`MDI_PWM_SafeStop`、`MDI_PWM_FaultActive` 和
  `MDI_PWM_ClearFault` 负责输出门控与故障锁存。

预装载、更新窗口、计数器启动顺序和高级定时器 MOE 由芯片后端负责，不能由公共宏猜测。

### Timer 与 Raw Tick

`MDI_TIMER_*` 控制可配置的外设定时器，负责频率、启动、停止和运行状态；Timer core
不注册 ISR 回调，板级中断向量确认标志后直接进入具体 driver 的 `IsrStep()`。

`MDI_TICK_Now(raw_tick)` 只读取无单位的原始 CPU 周期数。`MDI_TICK_Elapsed` 在宏展开点
保存静态基准，适合单个固定周期任务；需要多个动态周期或显式调度状态时，feature 自己
保存旧 tick 并进行无符号差值。毫秒、微秒阈值由板级 backend 提供的主频常量在使用模块
中编译期生成，core 不做运行时频率查询或除法换算。

### 板级 Service 与 Clock

`modus_Init()` 在 MODUS 对象初始化完成后调用一次 `mdi_Init()`；`modus_Run()` 在 MODUS
对象运行前调用一次 `mdi_Service()`；`modus_Clock()` 在对象的 Clock 回调前调用一次
`mdi_Clock()`。三个函数是板级扩展边界，不属于 `core/` 原语，也不传递运行时对象或函数表。

`mdi_Init()` 适合队列初始化、采样频率配置和其他一次性 MDI 状态准备；`mdi_Service()`
可以组合某个项目需要的 ADC DMA 消费、均值发布、下一批采样触发、板间链路维护或其他
前台硬件服务；`mdi_Clock()` 只适合 O(1) 的计数和超时状态维护。

`mdi_Service()` 可以组合某个项目需要的 ADC DMA 消费、均值发布、下一批采样触发、板间
链路维护或其他前台硬件服务；不同项目可以有不同内容。`mdi_Clock()` 只适合 O(1) 的
计数和超时状态维护，不做协议解析、均值计算或阻塞操作。DMA/USART 中断仍只处理硬件
标志、发布所有权或搬运字节，不能直接调用协议和应用逻辑。

### 总线和设备

`MDI_I2C_Transfer`、`MDI_SPI_Transfer` 是有界同步事务，缓冲区只在调用期间借用。硬件
I2C、软件 I2C、硬件 SPI 和软件 SPI 只要提供相同事务语义，就可以复用上层设备协议。
设备协议负责消息格式、片选或地址规则和设备状态机；它不负责选择芯片外设、GPIO 模式
或总线并发策略。具体传感器、存储器和显示器属于应用侧组合，不属于 core contract。

## 芯片后端职责

每个芯片至少提供一个实例头文件和对应后端：

```text
peripheral/<chip>/mdi/
├── instance.h       资源 token、引脚、通道和组合关系
├── backend.h        GPIO/ADC/PWM/总线的寄存器 provider
├── i2c.h / spi.h    外设事务和错误收敛
└── service.c         mdi_Init/mdi_Service/mdi_Clock
```

后端必须写清楚调用上下文、缓冲区生命周期、单位、范围、超时、完成时刻和并发所有权。
初始化不得藏在第一次读写中；前台事务不能偷偷进入实时控制中断；故障清除不能绕过
实时安全门控。

## 扩展和兼容

新增芯片时增加后端和实例，不复制一套公共 `mdi.h`。新增能力时优先放入 feature 并组合
现有 core 原语；只有协议边界、生命周期或实时性承诺无法由现有原语表达时，才增加新的
core contract。UART/Stream、DAC、Capture、Storage、DMA 等能力可以按同一规则独立加入；
CAN 保留为可选能力，不改变现有核心契约。

旧接口在 `legacy/` 中显式保留。迁移时先建立语义相同的静态资源，再替换应用调用；不
把旧对象和函数指针表重新包在宏后面。

## 验证要求

MDI 的最小验证分为三类：

- 主机契约：检查 IO、采样、PWM 以及 I2C/SPI 总线事务的行为；
- 负编译：检查错误资源类型、单位、能力和物理映射在编译期失败；
- 代码生成：在 `-O2/-Os` 下比较直接实现与 MDI 实现，确认热路径没有隐藏分派。

芯片后端还必须进行目标编译、链接和板级时序/故障验证。主机汇编通过不等于真实 GPIO
模式、DMA 缓存一致性、PWM 更新窗口或外设时序已经验收。
